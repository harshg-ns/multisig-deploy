Release Interlock

Three enrolled hardware keys. Any two of them sign the exact commit and artifact digest, the signed 24-hour queue elapses without anyone cancelling, and only then may the release execute. No single person — and no compromised laptop, stolen token or hostile agent — can complete it alone.

Why the pieces are shaped this way

Distinct humans The signer set is array (1 .. 8) of Boolean, indexed by enrolment slot. One holder presenting two signature files fills one slot. There is no counter to overflow and no list to deduplicate — two distinct signers is true by construction, not by a check.
Hardware The roster admits only sk-ssh-ed25519@openssh.com and sk-ecdsa-sha2-nistp256@openssh.com. Any signature OpenSSH accepts against that file was made by a hardware-resident key, so no signature blob has to be parsed to establish it. Enforced once, at the trust root.
The 24 hours Enforced, not asserted. The gap must be inside the signed bytes and must have elapsed against an internally-read clock. A queued release cannot shorten its own delay; there is no flag that changes the constant. GitHub's wait timer is the mechanism — an admin bypass resets a timer and cannot reset a signed value.
The cancel path A delay with no cancel path is just latency. Any quorum member appending the queued digest kills the release. An unparseable cancellation list counts as a cancellation.
No cryptography here ssh-keygen -Y verify, absolute path, argument vector, message on stdin, exit status only — never parsed output. OpenSSH is already the root of trust for NS commit signing; a second Ed25519 implementation would be a second thing to be wrong.
Sealed bytes OpenSSH is handed bytes, never a path. The manifest and roster slices that were parsed are copied into a file that is unlinked the instant it is written, so nothing in the filesystem names them and nothing can be swapped between the parse and the verification. Handing over paths instead was the critical bypass two adversarial audits found on 2 September; all six audit findings were in the unproved boundary code, not in the proved core.
Not YAML The manifest is eight fixed-width ASCII lines, so parsing is index arithmetic. Duplicate keys, reordered fields, anchors, tags, type coercion and unicode confusables aren't defended against — they aren't expressible.
No dependencies No package manager, no lockfile, no vendored source. The supply chain is GCC and OpenSSH, both already trusted by the rest of the release path. That constraint is what chose SPARK over Rust and Python.

What is still open

  • No signature from real hardware has been through this yet. Producing one needs a physical touch that no automated test can supply. The plumbing is proved end to end against real Ed25519 signatures, and -Y verify takes the same path for both key classes — but that is an argument, not a test. Bench-test with a YubiKey first.
  • The clock is trusted. Move the system clock past execute_after and the delay is retired. Nothing in the program can detect that.
  • Enrolment is assumed. That a roster key really was generated inside genuine hardware, with a touch required per signature, is established by FIDO attestation at enrolment and by whoever reviews the roster file — not here.
  • Build provenance is a separate step. The manifest names a digest; that the digest is what CI built from that commit must be checked in the same job.
  • A signature proves origin, never intent. Two genuine holders signing a malicious change passes every check, and always will.
  • The proof covers the decision, not the plumbing. Every defect found in this program so far has been in the 431 lines outside SPARK — the filesystem, the clock and the OpenSSH call. That is where the next one will be too.
